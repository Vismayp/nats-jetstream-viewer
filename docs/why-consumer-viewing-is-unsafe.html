NATS JetStream Viewer · Safety Design

Why a consumer cannot be a read-only message viewer

A JetStream consumer is a delivery state machine. Receiving through it changes delivery state even when the client does not send an ACK. That makes a consumer unsuitable for observing every stream without competing with workers or changing retention behavior.

Design decision: this viewer never creates, binds to, or fetches from a consumer. It reads stored messages with Stream Get or Direct Get, either directly or through the companion read-only HTTP gateway.

The required guarantees

The requested viewer must satisfy all of these conditions at the same time:

All retention policies

Inspect messages still stored in Limits, Interest, and WorkQueue streams.

No competition

Never take a delivery that should have gone to a real worker.

No acknowledgement

Never send ACK, NAK, TERM, progress, or any other consumer acknowledgement.

No delivery mutation

Do not advance a cursor, create ACK-pending state, increment attempts, or trigger redelivery.

A consumer fails at least one of these requirements. Storage retrieval satisfies them because it queries the stream's stored record instead of requesting delivery.

Why the requirements are mutually incompatible

This is not merely a limitation of the viewer implementation. It follows from what a JetStream consumer means: a consumer exists to select messages and ask the server to deliver them. Once delivery is requested, the server must account for who received the message and whether the work is complete.

Short proof: a consumer must use an acknowledgement policy. WorkQueue rejects AckNone. An explicit-ack consumer either ACKs, violating “no ACK,” or does not ACK, leaving the message assigned and pending, violating “no competition” and “no state change.” Therefore no consumer configuration satisfies all requirements.

Exhaust every possible acknowledgement choice

Consumer choiceWhat the server must doRequirement that fails
AckPolicy=None Deliver without waiting for a client ACK. WorkQueue cannot safely know that processing completed, so NATS rejects this consumer policy for WorkQueue streams. “All policies” fails because it cannot be used on WorkQueue.
AckPolicy=Explicit, then ACK Mark the delivery complete. On WorkQueue, the ACK makes the message eligible for immediate removal. “No ACK” fails, and viewing could delete work before a worker processes it.
AckPolicy=Explicit, do not ACK Record an outstanding ACK, keep the delivery assigned until AckWait, then redeliver it and increment attempts. “No competition” and “no state change” fail.
AckPolicy=All An ACK can cumulatively acknowledge this and earlier deliveries. Not ACKing has the same pending/redelivery problem as explicit ACK. Either “no ACK” or “no competition” fails; it also cannot provide the required WorkQueue explicit-ACK behavior.

Consumer placement does not solve it

Create a new viewer consumer

On WorkQueue, its filter cannot overlap the worker consumer. A non-overlapping filter sees only a partition, not all messages.

Share the existing worker consumer

The viewer becomes another worker in the pool. Delivery goes to either the viewer or a real worker, so the viewer necessarily competes.

The key distinction: observation versus delivery

A viewer wants to ask, “What bytes are currently stored at stream sequence 42?” A consumer asks, “Which message should this consumer receive next?” Those are different server operations with different semantics:

Storage observation:
  Stream Get(sequence=42) → return stored bytes
  No consumer selected, no delivery assigned, no ACK expected

Consumer delivery:
  Consumer Next() → select and assign work to this consumer
  Delivery cursor advances; ACK handling or redelivery must follow

Only the first operation can be guaranteed to be non-competing and acknowledgement-free across all retention policies.

A consumer is not a database read

A JetStream consumer stores server-side state: delivery policy, filter subjects, delivered sequence, acknowledgement floor, ACK-pending messages, redelivery attempts, waiting pulls, and optional limits. A fetch asks the server to perform delivery through that state machine.

Not sending an ACK does not undo delivery. For an explicit-ack consumer, the server has already assigned the message to that consumer, advanced its delivered sequence, and recorded the message as awaiting acknowledgement.

Why each consumer approach fails on WorkQueue

Approach 1: create an AckNone consumer

WorkQueue retention removes a message after a worker completes it and explicitly acknowledges it. NATS therefore requires WorkQueue consumers to use explicit acknowledgements. Creating an AckNone consumer is rejected by the server.

nats consumer add WORK viewer --pull --ack none --filter "jobs.>" --defaults

# Expected result:
# consumer creation fails because a WorkQueue consumer must use explicit ACKs

Approach 2: create a separate explicit-ack consumer

WorkQueue consumers cannot have overlapping filters because two consumers would claim the same work. If a real worker consumer already covers jobs.>, a viewer consumer with the same or overlapping filter is rejected.

# Existing worker covers jobs.>
nats consumer add WORK worker --pull --ack explicit --filter "jobs.>" --defaults

# Viewer overlaps the worker and should be rejected
nats consumer add WORK viewer --pull --ack explicit --filter "jobs.>" --defaults

Non-overlapping filters may be allowed, but that partitions the workload. It does not let the viewer inspect all messages.

Approach 3: bind the viewer to the worker's existing consumer

Multiple clients can pull from one consumer as a worker pool. If the viewer binds to that consumer, it joins the pool and competes with production workers. A message delivered to the viewer is temporarily unavailable to another worker until it is ACKed, NAKed, or redelivered after AckWait.

  1. The viewer requests one message from the worker consumer.
  2. The server assigns that job to the viewer and increments the delivered sequence.
  3. The viewer does not ACK, so outstanding ACKs increase.
  4. The real worker does not receive that job during the ACK wait.
  5. After timeout, the server redelivers it with a higher delivery-attempt count.

Operational consequences

  • Worker delay: work is held until timeout.
  • False redeliveries: delivery attempts increase even though processing never began.
  • MaxDeliver risk: repeated viewing can exhaust the configured delivery limit and terminate normal retries.
  • Backpressure: enough unacknowledged views can reach MaxAckPending and pause delivery.
  • Misleading monitoring: delivered sequence, ACK pending, redelivery count, and lag no longer represent worker activity alone.
  • Race conditions: a worker may ACK and remove a WorkQueue message while the viewer is displaying stale information.

Why “it works on Limits” is not enough

A separate consumer can be created on a Limits-policy stream, but it still advances delivery state and consumes server resources. On Interest retention, adding or delivering through a consumer can participate in the definition of whether a message still has interest. A universal viewer cannot switch to consumer delivery only for some policies without changing its safety model and observable behavior.

Reproducible CLI experiment

The following PowerShell experiment demonstrates both facts: AckNone creation fails, while an explicit-ack consumer can receive without ACK but changes delivery state and causes redelivery.

# Create a small WorkQueue stream
nats stream add WORK --subjects "jobs.>" --retention work --storage file --defaults
nats stream info WORK

# Publish one job
nats pub jobs.email "job-1"

# Test 1 — this must fail
nats consumer add WORK noack --pull --ack none --filter "jobs.>" --defaults

# Test 2 — explicit ACK consumer succeeds
nats consumer add WORK worker --pull --ack explicit --filter "jobs.>" --wait 2s --defaults

# Receive, but suppress the CLI ACK
nats consumer next WORK worker --count 1 --no-ack

# Observe Outstanding Acks = 1 and the message still stored
nats consumer info WORK worker
nats stream info WORK

# Wait past AckWait and fetch again
Start-Sleep -Seconds 3
nats consumer next WORK worker --count 1 --no-ack

# The same stream sequence is delivered again, normally with tries = 2
nats consumer info WORK worker
Interpretation: “I did not ACK” is not the same as “I did not consume.” The first fetch already changed consumer state and temporarily claimed the work.

The safe design when the central viewer cannot access NATS

Central viewerNo NATS connection
HTTPS →
Companion viewerBearer-protected GET endpoints
Storage Get →
JetStreamLimits, Interest, WorkQueue

The companion viewer is deployed inside the trusted network. Its NATS identity is restricted to stream listing, stream information, message Get/Direct Get, and optional consumer information. It has no ACK or mutation permissions. The central viewer talks to the companion through HTTPS and never opens a NATS connection.

Companion configuration

# Generate a random token
openssl rand -base64 32

# Set on the companion viewer
NJV_GATEWAY_TOKEN=<generated-token>

The companion exposes only bearer-protected GET /gateway/v1/* routes for health, stream metadata, and stored messages.

Central viewer configuration

  1. Open Connections and choose Read-only HTTP gateway.
  2. Enter the companion viewer's HTTPS base URL.
  3. Enter the direct NATS profile ID displayed by the companion.
  4. Enter the same gateway token.

The token is encrypted in the central viewer's configuration. Raw messages cross the gateway, and decoder scripts run in the central viewer.

Hard boundary

If neither the viewer nor any trusted companion is allowed to connect to NATS or invoke read-only JetStream storage APIs, live viewing is impossible. A consumer does not bypass that restriction—it is also a NATS connection using consumer API subjects. The remaining safe option is an administrator-configured republish into a separate Limits-policy audit stream or an approved external export pipeline.
